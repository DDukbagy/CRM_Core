# 예약 시 수강권 확인 · 고정

- 상태: 완료

- 브랜치 / PR: `crm`
- 관련 작업: [동시 요청 문제](pass-deduct-concurrency.md), [변이 테스트](test-mutation-check.md)

## 1. 문제

예약과 수강권이 연결돼 있지 않다.

- **예약 생성 때 수강권을 확인하지 않는다**: `backend/app/domains/booking/repository.py` `create` 는 슬롯·휴무·중복만 본다. 고객 앱은 활성 수강권이 없으면 화면에서 막지만(`apps/customer/app/(tabs)/schedule.tsx`), API 를 직접 부르면 수강권 없이 예약된다. 앱의 확인도 담당 강사와 상관없이 첫 번째 활성 수강권을 본다.
- **어떤 수강권에서 차감할지 예약에 없다**: `bookings` 에 수강권 칸이 없고, 완료·노쇼 때 `passes/repository.py` `deduct_for_lesson` 이 그 강사의 활성 수강권 중 먼저 발급된 것을 고른다. 같은 강사의 수강권이 여러 개면 고객이 쓰려던 수강권과 다른 것에서 차감될 수 있다.
- **완료 때가 돼서야 409**: 잔여 1회인 수강권으로 예약을 여러 개 잡을 수 있고, 두 번째부터는 강사가 완료할 때 "사용할 수 있는 수강권이 없습니다" 409 가 난다.
- **함께 확인할 것 (고치는 건 별도 항목)**: 고객 앱은 2시간 수강권이면 1시간 슬롯 2개를 골라 예약을 2건 만든다 (`schedule.tsx` 826행). 완료하면 레슨 1회에 2회가 차감될 수 있다.

## 2. 테스트 명세

- [ ] 1. 그 강사의 활성 수강권이 없는 고객이 예약하면 → 409를 반환하고 예약은 생기지않는다
- [ ] 2. 다른 고객의 수강권이나 다른 강사의 수강권을 지정해 예약하면 → 400을 반환하고 예약은 생기지않는다
- [ ] 3. 잔여 1회 수강권에 진행 중 예약이 1건 있는데 그 수강권으로 또 예약하면 → 409를 반환하고 예약은 생기지않는다 (첫 예약을 취소하면 가능해진다)
- [ ] 4. 같은 강사의 수강권이 2개일 때 나중 수강권을 지정해 예약하고 완료하면 → 지정한 수강권이 차감되어야한다

## 5. 선택지와 결정

**정한 범위**

- 수강권은 앱이 지정할 수 있고, 안 보내면 서버가 그 강사의 가장 오래된 쓸 수 있는 수강권을 고른다. 필수로 만들지 않은 것은 예전 버전 앱이 깨지지 않게 하기 위해서다.
- 2시간 수강권 이중 차감은 이번에 고치지 않고 별도 항목으로 한다 (8절). 예약 구조(예약 1건에 여러 시간)가 바뀌는 큰 작업이라 이번 변경과 섞지 않는다.

**1) 예약할 때 남은 횟수를 어떻게 확인하나** (예: 1회 남은 수강권으로 앞으로의 레슨을 3개 예약)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 진행 중 예약 수까지 빼고 확인 | 남은 횟수만큼만 예약된다. 완료 때 "수강권 없음" 409 가 나는 일을 예약 단계에서 막는다 | 예약할 때 진행 중 예약을 세야 하고, 동시에 예약해도 넘지 않게 수강권 행을 잠가야 한다 |
| B. 남은 횟수 > 0 만 확인 | 단순하다 | 1회 남아도 예약을 여러 개 잡을 수 있고, 두 번째부터는 완료 때 409 가 난다 |

- 고른 것: A. 
- 이유: 남은 횟수 > 0 만 확인하면 1회 남은 수강권으로도 예약을 여러 개 잡을 수 있고, 강사가 레슨을 마친 뒤 완료할 때 409 로 막힌다. 문제를 가장 늦게, 가장 곤란한 사람(이미 레슨을 한 강사)이 발견하게 되므로 예약 단계에서 막는 것이 맞다고 판단했다.

**2) 수강권 기록이 없는 기존 예약** (이 칸이 생기기 전에 만든 예약)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 비워 두고 완료 때 지금 방식(가장 오래된 수강권)으로 차감 | 데이터를 건드리지 않는다 | 차감 경로가 두 개로 남고, 정식 운영에는 없는 데이터를 위한 코드가 남는다 |
| B. 마이그레이션에서 채우고 DB 제약으로 막기 | 진행 중 예약은 항상 수강권이 있다. 차감 경로가 하나뿐이라 단순하다 | 원격 DB(개발·데모) 데이터를 바꾼다. 수강권이 없는 진행 중 예약은 취소해야 한다 |

- 고른 것: B (진행 중 예약은 그 강사의 수강권으로 채우고, 하나도 없으면 취소·사유 기록. 끝난 예약은 비워 둠). 처음에는 A 를 골랐다가 바꿨다.
- 이유: 처음에는 데이터를 건드리지 않는 A 를 골랐다. 그런데 수강권 칸이 빈 예약은 정식 운영 전 데이터(개발·데모)에만 있어서, A 는 운영에서 일어나지 않는 상황을 위해 차감 경로를 하나 더 남기는 셈이었다. 그래서 데이터를 한 번 정리하고 DB 제약으로 아예 생기지 않게 막는 B 로 바꿨다.

## 8. 남은 것

- **데모 DB 마이그레이션 (merge 전)**: 데모는 `staging` 을 따라가므로, 새 코드가 배포되기 전에 데모 DB 에 마이그레이션을 적용해야 한다. 적용 전에 개발 DB 와 같은 읽기 전용 조회로 취소될 예약 수를 확인한다
- 지정한 수강권이 본인·같은 강사 것이지만 다 썼거나 만료됐으면 400 이 아니라 409 다 (상태 문제라서). 명세에는 없는 경우라 동작만 적어 둔다
- 고객 앱은 담당 강사의 첫 활성 수강권을 보낸다. 같은 강사의 수강권이 여러 개일 때 고르는 화면은 없다 (서버는 지정을 받을 수 있음)

- **2시간 수강권 이중 차감 (별도 항목)**: 정책은 "레슨 한 번에 몇 회를 차감할지는 강사가 만든 수강권 정의를 따른다"(2시간 수강권 = 2시간 레슨 1회에 1회 차감). 지금은 슬롯마다 예약이 생겨 2회 차감될 수 있다.

## 9. 배운 것

처음에는 남의 수강권을 지정하거나 수강권 없이 예약하는 건 앱 화면에서 막고 있으니 일어날 수 없는 일이라고 생각했다. 그런데 재현 테스트를 돌려 보니 API 로 직접 보내면 수강권 없이도 예약이 그대로 만들어졌고, 앱의 확인도 담당 강사와 상관없이 첫 번째 수강권만 보고 있었다. "운영에서 불가능하다"는 정상 화면으로 못 한다는 뜻이 아니라 API 로 직접 보내도 서버가 막는다는 뜻이어야 한다는 것을 알았다. 반대로 수강권 칸이 빈 기존 예약처럼 운영에 존재하지 않는 상황은 테스트와 코드로 지키기보다 데이터를 정리하고 DB 제약으로 아예 생기지 않게 막는 편이 낫다는 것도 배웠다.
