# 강사 앱 일괄 완료

- 상태: 완료
- 기간: 2026-11-21 ~
- 브랜치 / PR: `crm`
- 관련 작업: [동시 요청 문제](pass-deduct-concurrency.md), [예약 시 수강권 확인·고정](booking-pass-pinning.md), [예약 1건 = 레슨 1회](booking-lesson-hours.md)

## 1. 문제

강사는 하루 레슨이 끝나면 그날 예약을 하나씩 열어 "완료"를 눌러야 한다. 예약마다 확인 창이 뜨고 요청이 따로 간다.

- 레슨이 여러 건인 날은 같은 동작을 건수만큼 반복한다.
- 앱이 요청을 여러 번 보내는 방식으로 묶으면, 중간에 하나가 거부됐을 때 어디까지 처리됐는지 화면이 알기 어렵다. 완료는 수강권을 차감하므로 "몇 건이 완료됐고 몇 건이 왜 안 됐는지"가 정확해야 한다.

## 2. 테스트 명세

- [ ] 1. 확정된 예약 3건(고객 2명)을 한 번에 완료하면 → 200 을 반환하고 3건 모두 완료 상태가 되며, 2건을 예약한 고객의 수강권은 2회, 1건을 예약한 고객의 수강권은 1회 차감된다
- [ ] 2. 3건 중 1건이 이미 취소된 예약이면 → 200 을 반환하고 나머지 2건은 완료·차감된다. 취소된 건은 결과에 실패와 이유가 담기고, 상태는 취소 그대로이며 차감되지 않는다
- [ ] 3. 같은 고객의 예약 2건을 보냈는데 그 고객의 수강권이 1회만 남았으면 → 200 을 반환하고 날짜가 빠른 1건만 완료되어 1회 차감된다. 늦은 1건은 결과에 실패와 이유가 담기고 확정 상태 그대로다
- [ ] 4. 목록에 다른 강사의 예약이 섞여 있으면 → 요청 전체가 404 로 거부되고, 내 예약도 완료되지 않으며 수강권은 차감되지 않는다
- [ ] 5. 목록에 없는 예약 번호가 섞여 있으면 → 요청 전체가 404 로 거부되고, 내 예약도 완료되지 않으며 수강권은 차감되지 않는다
- [ ] 6. 같은 예약 번호를 두 번 넣어 보내면 → 200 을 반환하고 그 예약은 한 번만 완료되며 수강권은 1회만 차감된다
- [ ] 7. 같은 일괄 완료 요청을 동시에 두 번 보내면 → 두 요청 모두 200 을 반환하고, 각 예약은 한 번만 완료되며 수강권은 예약 수만큼만 차감된다

## 3. 재현 (고치기 전)

- 테스트 이름 또는 실행한 명령: `make apitest ARGS="tests/test_booking_bulk_complete.py -p no:randomly --tb=line -q"` (`backend/tests/test_booking_bulk_complete.py` 7개)
- 실행 환경: 로컬 Postgres 컨테이너 (`make apitest`)
- 커밋: `0ede52b` + 테스트 파일

7개 모두 실패한다. 일괄 완료 주소가 없어서다.

```text
test_booking_bulk_complete.py:132: AssertionError: {"detail":"Not Found"}    ← 명세 2

test_booking_bulk_complete.py:203: AssertionError: {"detail":"Not Found"}    ← 명세 4 (잘못된 번호를 빼고 다시 보낸 요청, 기대 200)
test_booking_bulk_complete.py:228: AssertionError: {"detail":"Not Found"}    ← 명세 5 (같음)
test_booking_bulk_complete.py:242: AssertionError: {"detail":"Not Found"}    ← 명세 6

```

명세 4·5 는 "요청 전체가 404"를 기대하는데, 주소가 없으면 어떤 요청이든 404 다. 그래서 404 확인만으로는 고치기 전에도 통과해 버린다.
두 테스트는 "잘못된 번호를 빼고 다시 보내면 완료된다"까지 확인해, 주소가 없어서 나온 404 와 구분한다.

## 4. 원인

완료 API 가 예약 1건 단위(`PATCH /calendars/me/bookings/{id}/complete`)뿐이다. 여러 건을 한 요청으로 받아 건별 결과를 돌려주는 API 가 없다.

## 5. 선택지와 결정

**정한 범위**

- 앱이 요청을 여러 번 보내지 않고, 일괄 API 하나가 한 요청 안에서 순서대로 처리한다.
- 일괄 완료의 결과는 레슨 날짜가 빠른 순으로 하나씩 완료했을 때와 같다. 수강권이 1회 남은 고객의 예약 2건을 보내면 빠른 1건만 완료되고 나머지는 "수강권 없음"으로 거부된다.
- 다른 강사의 예약과 없는 예약 번호는 같은 응답(404)으로 거부한다. 남의 예약 번호가 있는지 드러나지 않게 하기 위해서다.
- 같은 번호가 두 번 들어 있으면 한 번만 처리한다.
- 확인 창에 "N명 · N건 · N회 차감" 요약을 보여 준다.
- 완료만 일괄로 한다(노쇼는 건별). 강사 앱에만 넣는다(웹은 나중에).

**1) 일부가 안 되면 어떻게 하나** (예: 5건 중 1건이 그사이 취소됐거나, 목록에 다른 강사의 예약이 섞여 있음)

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 전부 건별 결과: 되는 건은 완료하고, 안 되는 건은 이유와 함께 돌려준다 | 한 고객의 문제가 다른 고객의 완료를 막지 않는다 | 정상 앱이 보낼 수 없는 요청(남의 예약, 없는 번호)도 일부는 처리해 준다 |
| B. 전부 취소: 하나라도 안 되면 아무것도 완료하지 않는다 | 결과가 단순하다 | 그사이 취소된 1건 때문에 나머지 고객의 완료까지 다시 해야 한다 |
| C. 나눠서: 요청 자체가 잘못됐으면(남의 예약, 없는 번호) 전체 거부, 그사이 상태가 바뀐 것이면(취소됨, 수강권 모자람) 건별 결과 | 잘못된 요청은 아무것도 건드리지 않고, 정상 사용 중의 어긋남은 강사가 안 된 건만 다시 보면 된다 | 처리 전에 목록 전체를 먼저 검사해야 하고, 응답이 두 가지(전체 거부 / 건별 목록)가 된다 |

- 고른 것: C.
- 이유: 처음에는 일부가 안 되면 전부 건별 결과로 돌려주려 했다(A). 그런데 다른 강사의 예약이나 없는 번호는 정상 앱이 보낼 수 없는 요청이라, 섞여 있다면 앱 버그이거나 직접 호출이다. 그런 요청을 일부라도 처리해 주는 것보다 아무것도 건드리지 않고 거부하는 편이 안전하다고 봤다. 반대로 그사이 취소됐거나 수강권이 모자란 것은 강사가 정상적으로 쓰다가 만나는 일이라, 여기서 전부 막으면 한 건 때문에 다른 고객의 완료까지 다시 해야 한다. 예약 신청에서 "요청이 잘못됨"(400)과 "지금 상태와 충돌"(409)을 나눈 것과 같은 기준이다.

## 6. 수정

**백엔드**

- `backend/app/domains/booking/router.py`: `POST /calendars/me/bookings/complete` (강사·관리자).
- `backend/app/domains/booking/schemas.py`: 요청 `booking_ids`(1~50개), 응답 `results`(건별 `booking_id`·`ok`·`status`·`message`)·`completed`·`failed`.
- `backend/app/domains/booking/repository.py` `complete_many`
  - 먼저 목록 전체를 확인한다. 없는 번호나 다른 강사의 예약이 하나라도 있으면 아무것도 처리하지 않고 404.
  - 통과하면 레슨 날짜가 빠른 순으로 기존 단건 완료(`complete`)를 그대로 부른다. 그래서 상태 전환·차감·알림·로그가 단건과 같다.
  - 예약마다 따로 commit 한다. 409 로 거부된 건은 그 건만 되돌리고 이유를 결과에 담은 뒤 다음 건으로 넘어간다.
  - 같은 번호가 두 번 들어 있으면 한 번만 처리한다.

**API 계약**: 새 주소 하나 추가. 기존 응답은 바뀌지 않는다.

**DB**: 변경 없음.

**화면** — 강사 앱 대시보드 `apps/instructor/app/(tabs)/index.tsx`

## 8. 남은 것

- 레슨노트를 쓰면 그 예약이 바로 완료되게 하기, 대시보드에 레슨일지 작성 버튼: 별도 작업.
- 수업 후 3일이 지난 확정 예약을 자동으로 완료하기: 별도 작업. 이번에 만든 일괄 완료 로직을 쓰고, 하루 한 번 실행하는 수단을 따로 둔다.
- 웹에는 일괄 완료가 없다. 노쇼는 건별이다.
- 수강권 수동 수정이 "남은 횟수 < 진행 중 예약 수"를 만들 수 있다(명세 3 의 상태). 수정 단계에서 막는 것은 수강권 관리 작업에서 다룬다.

## 9. 배운 것

일괄 처리를 만들면서 트랜잭션의 경계를 어디에 두느냐가 "실패했을 때 무엇이 남는가"를 정한다는 것을 알게 됐다. 강사가 여러 고객의 예약을 한 번에 완료할 때 전체를 한 트랜잭션으로 묶으면, 한 고객의 수강권이 모자란 것만으로 성공해야 할 다른 고객의 완료까지 함께 되돌아간다. 그래서 예약마다 따로 커밋하고, 안 된 건만 되돌린 뒤 이유를 결과에 담아 돌려주게 했다. 다만 전부 건별로 처리하지는 않았다. 다른 강사의 예약이나 없는 번호처럼 요청 자체가 잘못된 경우는 처리 전에 먼저 걸러 아무것도 건드리지 않게 했는데, 예약 신청에서 400 과 409 를 나눴던 기준을 그대로 쓴 것이다. 같은 요청을 동시에 두 번 보내는 경우는 새 코드 없이 통과했다. 일괄 완료가 단건 완료를 그대로 부르게 만들어서, 동시 요청 작업 때 넣은 조건부 UPDATE 가 그대로 지켜 줬기 때문이다.
