# 수강권 관리: 동시 수정과 걸린 예약

- 상태: 완료
- 기간: 2026-11-23 ~
- 브랜치 / PR: `crm`
- 관련 작업: [동시 요청 문제](pass-deduct-concurrency.md), [예약 시 수강권 확인·고정](booking-pass-pinning.md), [강사 앱 일괄 완료](booking-bulk-complete.md)

## 1. 문제

강사가 수강권을 고치는 동작(횟수 추가, 수동 수정, 취소)이 두 가지를 보지 않는다.

- **동시에 오는 다른 요청**: `backend/app/domains/passes/repository.py` 의 `add_sessions`(횟수 추가)와 `update_customer_pass`(수동 수정)는 수강권을 읽고, Python 에서 계산한 뒤, 통째로 저장한다. 완료 처리의 차감이나 또 다른 수정과 겹치면 나중에 저장한 쪽이 앞의 결과를 덮어쓴다. [동시 요청 문제](pass-deduct-concurrency.md)에서 차감은 고쳤지만 이 두 동작은 그대로다.
- **그 수강권에 걸려 있는 예약**: 예약은 수강권 하나에 고정된다. 그런데 수강권을 취소하거나 사용 횟수를 올릴 때 진행 중인 예약이 몇 건 걸려 있는지 확인하지 않는다. 예약이 걸린 수강권을 취소하면 그 예약은 완료할 수 없는 채로 남는다.

## 2. 테스트 명세

- [ ] 1. 예약이 걸려 있는 수강권을 취소나 만료로 바꾸려 하면 → 409 를 반환하고 수강권은 진행 중 그대로 남는다. 이유에 걸려 있는 예약 수가 담긴다
- [ ] 2. 남은 2회에 예약 2건이 걸려 있는 수강권의 사용 횟수를 1 올리려 하면 → 409 를 반환하고 사용 횟수는 그대로다
- [ ] 3. 예약이 걸려 있는 수강권에 횟수를 추가하거나 메모를 고치면 → 200 을 반환하고 그대로 반영된다
- [ ] 4. 남은 1회 수강권의 마지막 완료(차감)와 횟수 5회 추가가 동시에 오면 → 둘 다 200 을 반환하고, 총 횟수는 5 늘고 사용 횟수는 1 늘며 수강권은 진행 중이다
- [ ] 5. 같은 수강권에 횟수 추가(3회, 5회)가 동시에 오면 → 둘 다 200 을 반환하고 총 횟수는 8 늘어난다
- [ ] 6. 사용 횟수를 직접 바꾸는 수정과 완료(차감)가 동시에 오면 → 둘 다 200 을 반환하고, 결과는 두 요청을 차례로 처리한 것과 같다(사용 횟수가 둘 중 한 순서의 값이고, 다 쓰지 않았으면 진행 중이다)

## 3. 재현 (고치기 전)

- 테스트 이름 또는 실행한 명령: `make apitest ARGS="tests/test_pass_management.py -p no:randomly --tb=line -q"` (`backend/tests/test_pass_management.py` 7개: 명세 1 은 취소·만료로 두 번)
- 실행 환경: 로컬 Postgres 컨테이너 (`make apitest`)
- 커밋: `9ca949b` + 예약 날짜 규칙 변경 + 테스트 파일

5개가 실패하고 2개는 통과한다. (응답 본문은 줄여 적음)

```text
test_pass_management.py:104: {"id":1, ... "status":"CANCELLED" ...       ← 명세 1: 예약 2건이 걸린 수강권이 취소됨 (200)
test_pass_management.py:104: {"id":2, ... "status":"EXPIRED" ...         ← 명세 1: 만료로도 바뀜
test_pass_management.py:120: {"id":3, ... "sessions_used":1 ...          ← 명세 2: 남은 1회에 예약 2건이 됨
test_pass_management.py:162: AssertionError: 5회가 남았는데 다 쓴 것으로 남으면 안 된다   ← 명세 4: 1/6회인데 상태는 "다 씀"
test_pass_management.py:177: AssertionError: 2 + 3 + 5                   ← 명세 5: 추가 한 번이 사라짐
5 failed, 2 passed
```

| 명세 | 기대 | 실제 (고치기 전) |
|---|---|---|
| 1. 예약이 걸린 수강권을 취소·만료 | 409 | 200, 바뀜. 걸린 예약은 완료할 수 없게 됨 |
| 2. 걸린 예약보다 남은 횟수가 적어지는 수정 | 409 | 200, 바뀜 |
| 3. 예약이 걸려 있어도 횟수 추가·메모 수정 | 200 | 200 (통과) |
| 4. 마지막 차감과 횟수 5회 추가가 겹침 | 6회 중 1회 사용, 진행 중 | 6회 중 1회 사용인데 "다 씀" |
| 5. 횟수 추가 3회·5회가 겹침 | 총 10회 | 한쪽만 반영 |
| 6. 수동 수정과 차감이 겹침 | 차례로 처리한 결과 | 같은 결과 (통과) |

3 은 규칙을 넣다가 함께 막지 않도록 지키는 테스트다. 6 은 지금도 결과가 맞는다. 수정이 사용 횟수 한 칸만 덮어써서, 완료 뒤에 수정한 것과 같아지기 때문이다. 고친 뒤에도 그대로인지 확인하는 용도로 남겼다.

겹치는 순서는 테스트가 정한다. 처음에는 두 요청이 같이 읽은 뒤 각자 저장하게만 했는데, 명세 4 는 추가 요청이 먼저 저장을 끝내면 우연히 맞는 결과가 나와 통과했다. 그래서 고치는 요청을 "읽은 뒤, 저장하기 전"에 멈춰 두고 그 사이에 완료를 끝내는 장치(`pass_gate.hold_write`)를 만들었다.

## 4. 원인

- `add_sessions`: `cp.sessions_total += sessions` 를 Python 에서 계산해 저장한다. 다 쓴 수강권을 다시 "진행 중"으로 돌리는 판단도 읽은 시점의 값으로 한다.
- `update_customer_pass`: 받은 값을 그대로 덮어쓰고, "사용 횟수 ≥ 총 횟수면 다 씀"도 읽은 시점의 값으로 판단한다. 걸려 있는 예약은 보지 않는다.
- 두 동작 모두 수강권 행을 잠그지 않는다. 예약 신청(`lock_passes_for_booking`)과 차감(`deduct_for_lesson`)은 잠그거나 조건부 UPDATE 를 쓴다.

## 5. 선택지와 결정

**정한 범위**

- 사용 횟수를 올려서 남은 횟수가 걸려 있는 예약 수보다 적어지게 하는 수정은 거부한다(409).
- 예약이 걸려 있어도 횟수 추가와 메모 수정은 그대로 된다.
- 횟수 추가·수동 수정이 완료의 차감이나 다른 수정과 겹치면, 결과는 두 요청을 차례로 처리한 것과 같아야 한다.

**1) 예약이 걸려 있는 수강권을 취소·만료로 바꾸려 하면**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 거부하고 걸린 예약 수를 알려 준다 | 예약이 완료할 수 없는 채로 남지 않는다. 예약을 어떻게 할지(취소, 다른 수강권으로 다시 예약)를 강사가 직접 정한다. 휴무 설정에서 예약이 있는 시간을 닫지 못하게 한 것과 같은 방식이다 | 수강권을 취소하려면 예약부터 하나씩 처리해야 한다 |
| B. 걸린 예약도 함께 취소한다 | 한 번에 끝난다 | 고객이 모르는 사이에 예약이 사라진다. 수강권을 실수로 취소하면 예약까지 되돌려야 한다 |

- 고른 것: A.
- 이유: 수강권을 취소하면서 예약까지 함께 취소하면 고객은 모르는 사이에 예약을 잃는다. 수강권을 실수로 취소했을 때 되돌려야 할 것도 늘어난다. 걸린 예약을 어떻게 할지는 건마다 사정이 다르므로(취소할지, 다른 수강권으로 다시 잡을지) 강사가 먼저 정하게 하고, 서버는 몇 건이 걸려 있는지만 알려 주기로 했다.

## 6. 수정

**백엔드** — `backend/app/domains/passes/repository.py`

- `_lock`: 저장 직전에 수강권 행을 잠그고(`SELECT ... FOR UPDATE`) 지금 값으로 다시 읽는다. `add_sessions` 와 `update_customer_pass` 가 계산하기 전에 부른다. 완료의 차감(조건부 UPDATE)과 예약 신청(행 잠금)도 같은 행을 기다리므로, 겹친 요청들이 차례로 처리된다.
- `_reserved`: 이 수강권에 걸려 있는 진행 중 예약 수.
- `update_customer_pass`
  - 진행 중인 수강권을 다른 상태(취소·만료·다 씀)로 바꾸려는데 걸린 예약이 있으면 409 와 "진행 중인 예약이 N건 있어 …"
  - 사용 횟수를 올려서 남은 횟수가 걸린 예약 수보다 적어지면 409
  - 횟수 추가, 메모 수정, 사용 횟수를 내리는 수정은 걸린 예약과 상관없이 된다

**API 계약**: 응답 형식은 그대로. 위 두 경우가 409 로 거부될 수 있다.

**DB**: 변경 없음.

**화면**: 바꾸지 않았다. 강사 앱 수강권 관리의 "수강권 취소"가 거부되면 서버가 준 이유가 그대로 뜬다.

## 8. 남은 것

- 수동 수정은 사용 횟수를 "이 값으로" 덮어쓰는 방식이라, 완료와 겹치면 완료의 차감 1회가 수정 값에 묻힌다(차례로 처리한 것과 같은 결과이긴 하다). 강사 앱 화면에는 사용 횟수를 직접 바꾸는 기능이 없고 API 에만 있다. "N회 더하기·빼기"로 바꿀지는 그 화면을 만들 때 정한다.
- 수강권을 취소하려면 걸린 예약을 먼저 하나씩 처리해야 한다. 걸린 예약을 한 번에 보여 주거나 함께 취소하는 화면은 없다.
- 이미 진행 중이 아닌 수강권에 예약이 걸려 있는 옛 데이터가 있으면 그 예약은 완료되지 않는다. 운영 데이터에는 없는 상태다.

## 9. 배운 것

동시 요청 문제는 차감에서 한 번 고쳤지만, 같은 수강권을 고치는 다른 두 동작에는 그대로 남아 있었다. 이번에는 조건부 UPDATE 대신 행을 잠그고 다시 읽는 방식을 썼다. 차감은 "남아 있으면 1 더하기"라 SQL 한 문장으로 끝나지만, 수정은 저장하기 전에 걸려 있는 예약 수를 확인하고 상태를 판단해야 해서 한 문장으로 쓸 수 없었기 때문이다. 테스트를 쓰면서는 두 요청을 동시에 보내는 것만으로는 부족하다는 것을 알았다. 횟수 추가가 먼저 저장을 끝내면 버그가 있어도 맞는 결과가 나와 테스트가 통과했고, 문제가 되는 순서를 테스트가 직접 만들어야 했다. 예약이 걸린 수강권을 취소하지 못하게 한 것은 예약이 있는 시간을 닫지 못하게 한 것과 같은 규칙이다. 외래 키는 가리키는 행이 지워지는 것만 막아 주고, 상태가 바뀌어 쓸 수 없게 되는 것은 코드가 지켜야 한다.
