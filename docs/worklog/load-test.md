# 부하 테스트 (더미 데이터 · Locust · p50/p95/p99)

- 상태: 완료
- 기간: 2026-11-18 ~ 2026-11-19
- 브랜치 / PR: `crm`
- 관련 작업: [DB 연결 성능 개선](../portfolio/performance-db-connection.md), [로깅 체계](structured-logging.md)

## 1. 문제

DB 연결 개선(`NullPool` → 커넥션 풀 5+5)의 효과는 "API 평균 1,473ms → 548ms" 로 적혀 있다. 이 값은 요청 하나를 10번 보낸 평균이라 두 가지를 보여 주지 못한다.

- **지연 분포**: 평균은 느린 꼬리(p95·p99)를 감춘다. 사용자가 "가끔 멈춘다"고 느끼는 건 꼬리 쪽이다.
- **동시 사용자**: 한 번에 한 요청만 보냈다. 풀은 최대 10개 연결이라 동시 요청이 그보다 많아지면 대기가 생긴다. 어디까지 버티는지 모른다.

로컬 Postgres 에서 연결 비용을 다시 쟀다 (30회 중앙값). 원격 Supabase 기준 새 연결은 약 860ms 였다.

```text
new conn+query median 26.9ms / reused query median 0.30ms
```

로컬은 연결 비용이 원격의 약 1/30 이라, 그대로 비교하면 풀 효과가 원래 문제보다 작게 나온다. 그래서 두 조건으로 잰다: ① 로컬 그대로 ② DB 앞에 지연 프록시를 두고 왕복 지연을 넣은 조건(예전 원격 왕복 77ms).

## 2. 측정 명세

- [ ] 1. 같은 데이터·같은 사용자 수에서 커넥션 풀은 NullPool 보다 → p50 뿐 아니라 p99 도 낮다
- [ ] 2. 사용자를 10→50→100명으로 늘리면 → 100명에서도 실패율 0%(풀 대기 시간 초과 없음)이고, p95가 10명일 때보다 급격히 늘지 않는다
- [ ] 3. DB 왕복 지연(77ms)이 있으면 → 풀과 NullPool의 차이가 지연 없을 때보다 훨씬 커진다
- [ ] 4. 사용자 100명까지 → 서버 오류는 없어야 한다

## 3. 측정 조건

| 항목 | 값 |
|---|---|
| 환경 | 로컬 PC (WSL2, 16코어), 로컬 Postgres 16 컨테이너, uvicorn 워커 1개 |
| 데이터 | 강사 20명, 고객 500명, 수강권 약 700개, 예약 약 1만 건 (지난 90일 + 앞으로 30일), 고정 seed |
| 네트워크 | ① 지연 없음 ② DB 앞 지연 프록시(toxiproxy). 프록시를 거친 쿼리 1번 77.3ms, 새 연결 + 쿼리 481ms (예전 원격은 860ms. 로컬은 TLS 가 없어 연결 단계가 짧다) |
| 요청 제한 | 측정 서버에서만 끔. 가상 사용자 전원이 같은 IP 라 IP 당 분당 200개 제한에 합쳐서 걸린다 (6절) |
| 비교 | `NullPool`(개선 전) vs 커넥션 풀 5+5(개선 후), 같은 데이터·같은 사용자 수·같은 시간 |
| 가상 사용자 | 10 → 50 → 100명, 단계마다 2분 |
| 시나리오 | 고객 4 : 강사 1. 고객은 빈 시간 조회 5 : 내 예약 3 : 내 수강권 2 : 예약 생성 1, 강사는 이번 주 예약 3 : 내 슬롯 1. 사용자마다 요청 사이 0.5~1.5초 쉼 |

## 4. 측정 방법

```bash
make loadseed    # 로컬 crm_load DB 를 새로 만들고 더미 데이터 넣기 (확인용)
make apiload     # 전체 측정: 네트워크 2 × 연결 방식 2 × 사용자 3단계, 끝나면 표 출력
make apiload NET=latency POOLS=pool STAGES="10" DURATION=30s   # 일부만
```

- **더미 데이터** (`backend/loadtest/seed.py`): 고정 seed. 지난 예약은 완료 80%·노쇼 5%·취소 15%, 앞으로의 예약은 확정 60%·신청 30%·취소 요청 5%·취소 5%. 일요일 정기 휴무와 강사마다 임시 휴무 2~4일. 수강권은 차감된 횟수만큼 앞 수강권부터 채워 다 쓴 것은 `COMPLETED`, 마지막 것은 `ACTIVE`, 고객 10명 중 1명은 `EXPIRED` 수강권이 하나 더 있다.
- **같은 출발점**: 측정 하나(조건 × 사용자 수)를 시작할 때마다 DB 를 지우고 같은 데이터를 다시 넣는다. 앞 측정에서 만든 예약이 다음 측정에 섞이지 않는다.
- **개선 전 재현** (`backend/loadtest/serve.py`): 앱 코드는 그대로 두고, 측정 서버 프로세스에서만 엔진을 `NullPool` 로 바꾼다 (`POOL=null`).
- **지연 조건**: DB 앞에 toxiproxy 컨테이너를 두고 보내는 쪽·받는 쪽에 각각 38ms 지연을 건다 (왕복 약 77ms).
- **토큰**: `make apiverify` 처럼 로컬 더미 비밀값으로 직접 서명한다. Supabase 에 연결하지 않는다.
- **성공 기준**: 조회는 2xx, 예약 생성은 `201`·`400`(휴무일)·`409`(이미 찬 시간). 아무 날짜·슬롯이나 고르므로 거절도 정상 응답이다. 그 밖의 코드와 5xx 는 실패.
- **수치**: Locust 의 백분위수는 근삿값이다 (100ms 이상은 유효숫자 2자리로 묶는다).

## 5. 선택지와 결정

DB 가 멀면(왕복 77ms) 풀 5+5 는 요청을 초당 약 20개까지만 처리한다. 그 이상은 줄을 서고, 10초 넘게 기다리면 500 이 된다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 그대로 두고 한계를 기록 | 코드 변경 없음. 실제 규모로는 초당 20개(분당 1,200개)에 닿기 어렵다. 운영에서 서버와 DB 를 같은 리전에 두면 왕복이 1~2ms 로 줄어 상한이 훨씬 올라간다 | 데모(Render ↔ Supabase)처럼 멀리 떨어진 배치에서는 한계가 그대로 남는다 |
| B. 풀 크기 키우기 (예: 10+10) | 설정 한 줄, 바로 재측정 가능. 상한이 대략 두 배가 된다 | Supabase 연결 수 한도(플랜마다 다름) 안이어야 한다. 서버를 여러 대 띄우면 대수 × 풀 크기만큼 연결이 필요하다. 원인(왕복 수)은 그대로다 |
| C. 요청당 쿼리 수 줄이기 | 원인을 줄인다. 요청마다 연결을 쓰는 시간이 줄어 모든 조건에서 빨라진다 | 코드 변경이 크다. 빈 시간 조회·예약 같은 거래 도메인이라 테스트가 같이 필요하다 |
| D. 연결 대기 시간을 줄여 빨리 실패 | 10초 동안 붙잡혀 있지 않고 빨리 오류를 돌려준다 | 처리량은 그대로고 실패만 빨라진다. 문제를 푸는 게 아니다 |

- 고른 것: B. 풀 크기 키우기 (10+10)
- 이유: 지연 77ms + 100명에서 연결 대기 시간 초과 500 이 실제로 났고, 처리량이 초당 20.1개에서 멈춰 계산한 상한(연결 10개 ÷ 0.45초 ≈ 22개)과 맞았다. 그리고 Supabase 한도(최대 60, 권장 48) 안에서 Pool Size 를 30 으로 올리면 해결할 수 있었기 때문이다.

## 6. 바꾼 것

- **풀 크기** (`backend/app/db/session.py`): `pool_size=5, max_overflow=5` → `pool_size=10, max_overflow=10` (최대 연결 10 → 20)
- **Supabase Session pooler Pool Size** (데모·개발 프로젝트 대시보드): 15 → 30. Session pooler 는 클라이언트 연결 수를 Pool Size 로 제한해서, 앱이 20개를 열려면 그보다 커야 한다. DB 최대 연결은 60, Supabase 권장 상한은 그 80%(48). 30 = 앱 20 + 마이그레이션·대시보드·배포 중 서버 두 대 겹침 여유
- 영향 범위: 이 설정을 쓰는 모든 서버(로컬 `make api`, 데모 Render, 이후 AWS). API 계약·DB 스키마·웹·앱 없음

측정 도구도 추가했다.

- 추가: `backend/loadtest/` (`seed.py`, `people.py`, `serve.py`, `locustfile.py`, `run.sh`, `report.py`, `requirements.txt`), `Makefile` 의 `loadseed`·`apiload`
- Locust 는 앱 의존성(`pyproject.toml`)에 넣지 않고 `backend/loadtest/.venv` 에 따로 설치한다
- 영향 범위: API 계약·DB 스키마·웹·앱 없음. 원격 DB 에 연결하지 않는다

1차 측정은 버렸다. 측정 장치 문제 두 가지가 있었다.

- **실패율 31~47% 가 전부 429**: 앱의 요청 제한(IP 당 분당 200개, `app/main.py`)에 가상 사용자 100명이 합쳐서 걸렸다. 모두 127.0.0.1 에서 보내기 때문이다. 커넥션 풀이 아니라 요청 제한을 잰 셈이라, 측정 서버에서만 요청 제한을 끄고 다시 쟀다 (`serve.py`).
- **측정이 끝난 뒤의 500 (`relation "users" does not exist`)**: uvicorn 은 종료 신호를 받아도 처리 중인 요청을 끝낼 때까지 돈다. 그 사이 다음 측정을 위해 DB 를 지워서 남은 요청이 실패했다. Locust 가 끝난 뒤라 통계에는 들어가지 않았지만, 서버가 완전히 꺼진 뒤에 DB 를 지우도록 고쳤다 (`run.sh`).

2026-11-19 측정 (2차). 단위 ms. 전체 요청을 합친 값(Locust `Aggregated`). 엔드포인트별 값은 `make apiload` 출력 표에 있다.

**③ 풀 10+10 으로 바꾼 뒤 (같은 데이터·사용자 수·시간)**

| 조건 | 사용자 | 풀 5+5: 초당 요청 / p50 / p95 / p99 / 실패율 | 풀 10+10: 초당 요청 / p50 / p95 / p99 / 실패율 |
|---|---|---|---|
| 지연 없음 | 10 | 9.9 / 8 / 12 / 31 / 0% | 10.0 / 8 / 12 / 31 / 0% |
| 지연 없음 | 50 | 49.9 / 8 / 18 / 170 / 0% | 49.8 / 8 / 16 / 92 / 0% |
| 지연 없음 | 100 | 98.0 / 10 / 82 / 230 / 0% | 98.0 / 11 / 43 / 430 / 0% |
| 지연 77ms | 10 | 6.3 / 550 / 1,300 / 1,600 / 0% | 6.6 / **480** / **870** / **1,500** / 0% |
| 지연 77ms | 50 | 19.8 / 1,400 / 2,200 / 3,400 / 0% | **32.5** / **550** / **960** / **1,800** / 0% |
| 지연 77ms | 100 | 20.1 / 3,800 / 4,700 / 7,800 / 0.04% (500 1건) | **39.6** / **1,400** / **2,300** / **3,400** / **0%** |

- 지연 77ms + 100명: 처리량이 초당 20.1 → 39.6개로 거의 두 배가 됐고, p50 3,800 → 1,400ms, p99 7,800 → 3,400ms, 연결 대기 시간 초과 500 은 없어졌다. NullPool(2,700 / 6,400ms)보다도 빨라졌다.
- 지연 77ms + 50명: 풀 5+5 에서는 이미 줄이 생겼지만(p50 1,400ms) 10+10 에서는 10명일 때와 거의 같다(550ms).
- 상한은 없어진 게 아니라 올라간 것이다. 계산상 20 ÷ 0.45초 ≈ 초당 44개이고, 100명에서 39.6개라 p50 이 10명일 때(480ms)보다 세 배 가까이 늘었다.
- 지연 없음은 연결이 모자라지 않던 조건이라 차이가 거의 없다. 100명의 p99 230 → 430ms 는 두 번 잰 값의 흔들림 범위로 보이며, 풀을 키워서 생긴 차이라고 볼 근거는 없다.

**명세 판정 (풀 5+5 기준)**

| 명세 | 결과 | 근거 |
|---|---|---|
| 1. 풀은 p50 뿐 아니라 p99 도 낮다 | **조건부 성립** | 지연 없음은 모든 단계에서 성립 (p99 130→31, 1,200→170, 2,900→230). 지연 있음은 10·50명에서 성립, **100명에서 뒤집힘** (p99 6,400 vs 7,800) |
| 2. 100명에서도 실패율 0%, p95 가 급격히 늘지 않는다 | **지연 없음: 성립 / 지연 있음: 실패** | 지연 없음 p95 12→18→82ms, 실패 0%. 지연 있음 p50 550→1,400→3,800ms 로 늘고 처리량이 초당 약 20개에서 멈췄다. 100명에서 연결 대기 시간 초과 500 이 1건 |
| 3. 지연이 있으면 풀과 NullPool 의 차이가 더 커진다 | **10명에서만 성립** | 10명 p50 차이: 지연 없음 33ms(41→8), 지연 있음 750ms(1,300→550). 사용자가 늘면 차이가 줄고 100명에서는 풀이 더 느리다 |
| 4. 100명까지 서버 오류가 없다 | **실패 (지연 있음, 풀)** | `QueuePool limit of size 5 overflow 5 reached, connection timed out, timeout 10.00` 1건. 지연 없음과 NullPool 은 0건 |

풀 10+10 에서는 2·4번이 지연 77ms 에서도 실패율 0%·서버 오류 0건이 됐다. 다만 100명에서 p50 이 10명일 때의 약 세 배라 "p95 가 급격히 늘지 않는다"는 여전히 성립하지 않는다 (상한 근처).

**왜 지연 있음 + 100명에서 풀 5+5 가 더 느렸나**

- 풀은 연결이 최대 10개다. 요청 하나는 쿼리 5~6개를 보내므로, 왕복 77ms 면 연결 하나를 약 0.45초 붙잡는다.
- 연결 10개 ÷ 0.45초 ≈ **초당 22개가 상한**이다. 측정된 처리량이 초당 20.1개에서 멈췄다.
- 그 이상 들어온 요청은 연결이 빌 때까지 줄을 선다. 서버 쪽에서 잰 처리 시간의 중앙값도 3,811ms 로, 대부분이 줄 선 시간이다. 10초 넘게 기다린 요청은 500 이 됐다.
- NullPool 은 연결 수 상한이 없다 (Postgres `max_connections` 100 까지). 요청마다 연결 비용(481ms)을 내지만 줄을 서지 않아서 이 구간에서는 오히려 빨랐다.
- 지연이 없으면 연결 하나를 몇 ms 만 쓰므로 상한이 훨씬 높아 100명에서도 줄이 생기지 않았다.

## 8. 남은 것

- **요청당 쿼리 수 줄이기 (5절 C, 다음 항목)**: 쿼리 수를 세어 보니 빈 시간 조회 5개, 예약 생성 7개(`time_slots`·`users` 두 번씩), 내 수강권 4개(`users` 두 번)이고, 모든 요청의 첫 쿼리가 로그인 사용자 조회다. 중복을 줄이면 요청마다 연결을 쓰는 시간이 줄어 상한이 더 오른다. 거래 도메인 코드라 별도 항목으로 한다.
- 풀 10+10 의 상한은 지연 77ms 기준 초당 약 44개다. 서버를 여러 대 띄우면 대수 × 20 이 Supabase Pool Size(30) 안이어야 하므로, 늘릴 때 Pool Size 도 같이 본다.
- 측정은 로컬 PC 한 대에서 Locust 와 서버를 같이 돌렸다. uvicorn 워커 1개다. 실서비스 수치가 아니다.
- 77ms 는 예전 개발 환경(Codespace ↔ Supabase)의 왕복이다. 운영에서 서버와 DB 를 같은 리전에 두면 왕복이 훨씬 짧아져 상한도 올라간다.
- Locust 백분위수는 근삿값이다.
