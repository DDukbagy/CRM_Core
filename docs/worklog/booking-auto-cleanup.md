# 지난 예약 자동 정리 (자동 완료 · 자동 취소)

- 상태: 완료
- 기간: 2026-11-24 ~ 2026-11-25
- 브랜치 / PR: `crm` / #97
- 관련 작업: [일괄 완료](booking-bulk-complete.md), [예약 날짜 규칙](booking-date-rules.md), [레슨노트 작성 = 완료](lesson-note-completes-booking.md)

## 1. 문제

수업이 끝난 예약을 강사가 완료 처리하지 않으면 확정 상태로 계속 남는다. 수강권은 차감되지 않고, 고객의 남은 횟수와 매출 통계가 실제와 어긋난다.

수업 날짜가 지나도록 강사가 답하지 않은 신청도 남는다. 날짜 규칙상 더는 확정할 수 없는데 대시보드 숫자에는 계속 잡히고, 신청 관리 목록의 조회 범위(90일)를 벗어나면 화면에서 찾을 수도 없다.

정한 것 (2026-11-22 ~ 11-24)

- 수업일 + 3일이 지난 확정 예약은 자동으로 완료하고 수강권을 1회 차감한다. 강사와 고객 모두에게 알린다
- 수업 날짜가 지난 신청은 자동으로 취소한다. 신청을 자동으로 확정하지는 않는다
- 수업일이 지난 "취소 신청 중" 예약은 건드리지 않는다. 차감할지는 강사가 정한다
- 차감할 수 없는 확정 예약(수강권을 다 씀)은 확정으로 남기고 로그를 남긴다
- 실행: 규칙은 백엔드 저장소 계층에 두고, 비밀 값으로 보호한 주소를 예약 실행이 하루 한 번 부른다

## 2. 테스트 명세

"어떤 상황에서 → 무엇이 일어나야 한다" 형식.

있는 것과 가질 수 있는 값

| 있는 것 | 가질 수 있는 값 |
|---|---|
| 예약 상태 | 신청 중 · 확정 · 취소 신청 중 · 완료 · 노쇼 · 취소됨 |
| 수업일과 오늘 | 앞날 · 당일 · 1~3일 지남 · 4일 이상 지남 |
| 고정된 수강권 | 남은 횟수 있음 · 다 씀 |
| 한 번에 정리할 예약 | 없음 · 한 건 · 여러 건 (그중 일부만 실패) |
| 호출할 때 보낸 비밀 값 | 맞음 · 틀림 · 안 보냄 · 서버에 설정되지 않음 |
| 실행이 겹치는 경우 | 같은 날 두 번 · 동시에 두 번 · 강사의 완료 요청과 동시에 |
| 결과로 확인할 것 | 예약 상태 · 수강권 사용 횟수 · 시간을 차지하는지(취소) · 취소 사유 · 응답의 건수 |

요청은 모두 자동 정리 실행(`POST /internal/bookings/cleanup`)이다. "3일이 지난"은 수업일 + 4일째부터다 (11-20 수업이면 11-24 실행에서 완료).

- [x] 1. 수업일 + 3일이 지난 확정 예약이 있으면 → 200 을 반환하고 그 예약은 완료 상태가 되며 수강권이 1회 차감된다. 응답의 완료 건수는 1 이다
- [x] 2. 수업 후 3일째인 확정 예약은 → 확정 그대로이고 차감되지 않는다
- [x] 3. 수업 날짜가 지난 신청은 → 취소되고 취소 사유가 남으며, 시간을 더 차지하지 않고 수강권은 차감되지 않는다. 응답의 취소 건수는 1 이다
- [x] 4. 수업 당일인 신청은 → 신청 중 그대로다
- [x] 5. 수업일 + 3일이 지난 '취소 신청 중' 예약은 → 그대로 두고 차감하지 않는다. 응답에 건수로만 잡힌다
- [x] 6. 3일이 지난 확정 예약 2건 중 1건의 수강권을 다 썼으면 → 차감할 수 있는 1건만 완료되고 다른 1건은 확정 그대로 남는다. 응답은 완료 1, 남긴 건 1 이다
- [x] 7. 자동 정리를 같은 날 두 번 실행하면 → 두 번째는 아무것도 처리하지 않고 수강권은 1회만 차감된 채다
- [x] 8. 비밀 값이 틀리거나 없으면 → 401 로 거부되고 아무것도 바뀌지 않는다
- [x] 9. 서버에 비밀 값이 설정되지 않았으면 → 어떤 값을 보내도 404 다

명세에 넣지 않은 것: 강사의 완료 요청과 자동 정리가 동시에 오는 경우. 둘 다 같은 조건부 UPDATE 를 거치고, 그 동작은 `test_concurrency.py` 와 `test_booking_bulk_complete.py` 가 이미 확인한다.

## 4. 원인

지난 예약을 정리하는 주체가 강사뿐이었다. 완료·거절은 강사가 누를 때만 일어나고, 누르지 않은 예약을 대신 처리하는 것이 없었다.

## 5. 선택지와 결정

**무엇이 자동 정리를 실행하는가**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 비밀 값으로 보호한 주소를 바깥의 예약 실행(GitHub Actions)이 하루 한 번 부른다 | 서버가 한 대든 여러 대든 한 번만 실행된다. 규칙은 저장소 계층에 있어 날짜를 옮겨 테스트할 수 있다. 실행 주체만 나중에 바꾸면 된다 | 바깥에서 부를 수 있는 주소가 하나 생긴다. 비밀 값을 두 곳(서버, GitHub)에 넣어야 한다 |
| B. 백엔드 프로세스 안에서 타이머로 실행한다 | 바깥 설정이 필요 없다 | 서버가 여러 대면 여러 번 실행된다. 잠드는 서버(데모)에서는 돌지 않을 수 있다 |

- 고른 것: A
- 이유: 차감이 일어나는 작업이라 "정확히 누가, 언제 실행했는지"가 분명해야 한다. 같은 실행이 겹쳐도 조건부 UPDATE 가 막아 주지만, 겹칠 일을 처음부터 만들지 않는 쪽이 낫다

**수업일이 지난 '취소 신청 중' 예약**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 건드리지 않는다 | 차감 여부를 사람이 정한다 | 강사가 답하지 않으면 계속 남는다 |
| B. 3일 뒤 완료(차감) | 남는 예약이 없다 | 고객은 취소를 신청했는데 차감된다 |
| C. 3일 뒤 취소(차감 없음) | 남는 예약이 없다 | 수업을 실제로 했어도 차감되지 않는다 |

- 고른 것: A
- 이유: 수업을 했는지 안 했는지를 서버가 알 수 없다. 어느 쪽으로 정해도 한쪽에게는 틀린 결과가 된다. 건수는 응답과 로그에 남긴다
