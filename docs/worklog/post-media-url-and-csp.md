# 게시물 미디어 주소 검사와 웹 보안 헤더

- 상태: 완료
- 기간: 2026-11-26
- 브랜치 / PR: `crm` / #100
- 관련 작업: [웹 세션 쿠키 HttpOnly](web-cookie-httponly.md)

## 1. 문제

게시물의 미디어 주소(`url`)는 강사가 보낸 문자열을 그대로 저장했고, 웹과 두 앱은 그 주소를 그대로 이미지·영상 주소로 썼다. 형식 검사가 없어서 다른 사이트의 주소나 `javascript:` 같은 주소도 저장됐다.

조사하다가 더 큰 문제를 찾았다. 서버는 저장된 주소가 S3 주소처럼 보이면(`…amazonaws.com`) 경로를 객체 키로 삼아 **우리 버킷의** 임시 서명 주소를 만들어 응답에 넣는다. 버킷이 맞는지, 어느 폴더인지는 보지 않았다. 그래서 강사가 게시물 미디어 주소에 다른 강사의 레슨노트 PDF 경로를 넣으면, 비공개 파일을 열 수 있는 서명 주소가 게시물 응답에 실려 나온다.

웹에는 브라우저에게 "어디서 온 스크립트·이미지만 허용한다"를 알려 주는 보안 헤더(CSP)가 없었다.

## 2. 테스트 명세

"어떤 상황에서 → 무엇이 일어나야 한다" 형식. 요청은 강사가 미디어 주소를 넣어 게시물을 만드는 것이다.

- [ ] 1. 우리 버킷의 게시물 폴더에 있는 https 주소는 → 201 로 저장된다 (임시 서명이 붙은 주소도 같다)
- [ ] 2. https 가 아니거나(http, javascript:, data:) 다른 사이트의 주소면 → 400 으로 거부되고 게시물은 만들어지지 않는다
- [ ] 3. 다른 버킷의 S3 주소면 → 400 으로 거부된다
- [ ] 4. 우리 버킷이지만 게시물 폴더가 아닌 주소(레슨노트 PDF 등)면 → 400 으로 거부된다
- [ ] 5. 게시물을 수정할 때도 같은 규칙이다 → 400 이고 기존 미디어는 그대로 남는다
- [ ] 6. 미디어 종류가 IMAGE·VIDEO 가 아니면 → 422

## 4. 원인

- 미디어 주소는 타입이 문자열이라는 것 말고는 확인하는 곳이 없었다
- 객체 키를 뽑는 함수(`s3_key_from_url`)는 주소의 호스트가 `.amazonaws.com` 으로 끝나는지만 봤다. 서명 주소를 만드는 쪽은 그 키를 우리 버킷의 키로 믿고 썼다
- 화면은 자기가 올린 파일의 주소만 보내므로 정상 사용에서는 드러나지 않았다

## 5. 선택지와 결정

**웹 CSP 의 스크립트 규칙을 어디까지 조이는가**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `script-src 'self' 'unsafe-inline'` | 설정 한 곳(`next.config.ts`)으로 끝난다. 지금의 정적 렌더링이 그대로다. 다른 사이트의 스크립트 불러오기, 다른 사이트로 보내기, 틀 안에 넣기는 막는다 | 페이지 안에 끼어든 인라인 스크립트는 막지 못한다 |
| B. 요청마다 nonce 를 붙이고 `'unsafe-inline'` 을 없앤다 | 인라인 스크립트까지 막는다 | 모든 페이지가 요청마다 렌더링된다. 프록시에서 헤더를 만들고 nonce 를 전달하는 코드가 필요하다 |

- 고른 것: A
- 이유: 이 웹은 사용자가 쓴 글을 HTML 로 넣는 곳이 없고(React 가 글자로 바꿔 출력한다), 위험한 출력 API 를 쓰는 곳도 없다. 인라인 스크립트가 끼어들 경로가 지금은 없어서, 바깥 자원과 전송을 막는 것만으로 얻는 것이 크다. B 는 모든 화면의 렌더링 방식을 바꾸는 일이라 따로 다룬다

## 8. 남은 것

- 이미 저장된 게시물 미디어는 검사하지 않았다. 규칙에 맞지 않는 주소가 운영·데모 DB 에 있는지는 확인하지 않았다 (있다면 그 게시물은 미디어를 그대로 둔 채로는 수정되지 않는다)
- 웹에서 사진을 실제로 S3 에 올리는 흐름은 CSP 를 켠 상태로 확인하지 못했다 (로컬에 S3 가 없다). 배포 후 한 번 올려 봐야 한다
- CSP 의 `'unsafe-inline'` (5절 B)
- Vercel 미리보기 배포의 댓글 도구는 다른 사이트의 스크립트라 막힐 수 있다 (운영 배포와는 무관)
