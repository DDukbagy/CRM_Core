# 예약 1건 = 레슨 1회 (여러 시간 예약)

- 상태: 완료
- 기간: 2026-11-20 ~
- 브랜치 / PR: `crm`
- 관련 작업: [예약 시 수강권 확인·고정](booking-pass-pinning.md), [동시 요청 문제](pass-deduct-concurrency.md)

## 1. 문제

수강권은 "회당 N시간"(`duration_hours`)으로 정의되는데, 예약은 1시간 슬롯 1개만 가질 수 있다. 그래서 2시간 레슨 1회가 예약 2건이 되고, 횟수를 세는 곳이 모두 어긋난다.

- **2시간 레슨을 완료하면 2회 차감된다**: 고객 앱이 슬롯마다 `POST /bookings` 를 따로 보내고(`apps/customer/app/(tabs)/schedule.tsx` `submitBooking`), 완료는 예약마다 1회 차감한다. 수강권 정의는 "2시간 레슨 1회 = 1회"다.
- **1회 남은 2시간 수강권으로는 예약이 반쪽만 된다**: 남은 횟수 확인이 진행 중 예약 건수로 세므로 첫 슬롯은 201, 둘째 슬롯은 409 가 되고 1시간짜리 예약만 남는다.
- **요청이 따로 가서 반쪽 예약이 남는다**: 두 슬롯 중 하나를 다른 고객이 먼저 잡아도 나머지 하나는 예약된다.
- **강사 앱은 묶어 보여 주지만 첫 예약만 처리한다**: 시간이 이어진 예약을 카드 하나로 그리는데(`makeBookingGroups`), 확정·완료 버튼은 묶음의 첫 예약에만 간다. 어느 예약들이 한 레슨인지는 화면의 추측일 뿐 서버에는 없다.

[예약 시 수강권 확인·고정](booking-pass-pinning.md) 작업 중 발견했다.

## 2. 테스트 명세

- [ ] 1. 2시간 수강권으로 이어진 슬롯 2개를 예약하고 강사가 확정·완료하면 → 강사가 확정하면 예약은 1건 생기고, 강사가 완료처리하면 해당 고객의 수강권은 1회만 차감된다
- [ ] 2. 1회 남은 2시간 수강권으로 이어진 슬롯 2개를 예약하면 → 신청이 정상적으로 진행된다
- [ ] 3. 2시간 수강권인데 슬롯을 1개만(또는 3개) 보내면 → 400를 반환하고 예약은 진행되지않는다
- [ ] 4. 2시간 수강권으로 이어지지 않은 슬롯 2개(예: 10시, 14시)를 보내면 → 400를 반환하고 예약은 진행되지않는다
- [ ] 5. 고른 슬롯 2개 중 하나가 이미 다른 고객의 예약이면 → 409를 반환하고 예약은 진행되지않는다
- [ ] 6. 2시간 예약을 철회한 뒤 그 두 시간을 다시 예약하면 → 예약이 가능하다
- [ ] 7. 두 고객이 한 시간이 겹치는 2시간 예약(10~12시, 11~13시)을 동시에 보내면 → 둘 중 하나만 201, 나머지는 409 이고 예약은 1건만 남는다

## 4. 원인

"레슨 1회"를 나타내는 데이터가 없다.

- `backend/app/domains/booking/models.py` `Booking.time_slot_id`: 예약 1건이 슬롯 1개만 가리킨다. 같은 날짜·슬롯의 중복은 `bookings` 의 유니크 인덱스(`uq_booking_lesson_slot_date`)가 막는다.
- `backend/app/domains/booking/schemas.py` `BookingCreate.time_slot_id`: 요청도 슬롯 1개만 받는다.
- `backend/app/domains/booking/repository.py` `_pin_pass`·`_deduct_pass`: 남은 횟수 확인과 차감이 예약 건수 기준이다. 예약 1건이 레슨 1회라면 맞는 계산인데, 2시간 레슨이 2건으로 들어와서 틀려진다.
- `apps/customer/app/(tabs)/schedule.tsx` `submitBooking`: `duration_hours` 만큼 고른 슬롯을 요청 여러 개로 나눠 보낸다.
- `apps/*/lib/bookingUtils.ts` `makeBookingGroups`: 서버에 묶음이 없어 화면이 "시간이 이어지면 같은 레슨"으로 추측한다.

## 5. 선택지와 결정

**정한 범위**

- 예약이 갖는 시간은 슬롯 목록으로 저장한다(`booking_slots`). 가용 시간과 휴무(`calendar_blocks`)가 슬롯 번호 기준이라, 시작·끝 시각으로 바꾸면 달력 도메인까지 다시 짜야 한다.
- 슬롯 수는 고정된 수강권의 `duration_hours` 와 같아야 하고 시간이 이어져야 한다. 화면은 이미 그렇게 고르지만 API 를 직접 부르면 어길 수 있으므로 서버에서 막는다.
- 기존 예약은 각자 슬롯 1개짜리 예약으로 옮긴다.
- 응답의 `time_slot_id` 는 없애고 `time_slot_ids` 로 바꾼다. 첫 슬롯만 담은 값을 남기면 같은 사실이 두 군데에 생긴다.

**1) 레슨 1회를 어떻게 표현하나**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 예약은 슬롯당 1건 그대로, 같은 레슨끼리 묶음 번호 | 슬롯 중복 인덱스·가용 시간 조회·응답 형식이 거의 그대로다. 바뀌는 곳이 적다 | 예약 1건이 레슨 1회가 아니다. 확정·취소·완료·차감·남은 횟수 계산을 모두 "묶음 단위"로 다시 써야 하고, 묶음 안 일부만 취소된 상태가 생길 수 있다 |
| B. 예약 1건 = 레슨 1회, 예약이 슬롯 여러 개를 가짐 | 차감·남은 횟수·상태 전환이 지금 코드 그대로 맞는다. 일부만 취소된 레슨이 구조상 없다 | 슬롯 중복 인덱스를 옮겨야 하고, 가용 시간 조회·응답 형식·세 화면이 함께 바뀐다 |

- 고른 것: B.
- 이유: 수강권이 "회당 N시간"으로 정의돼 있으므로 예약 1건이 레슨 1회이고, 그 1회가 1시간일 수도 2·3시간일 수도 있다고 보는 것이 실제와 맞다. A 는 바뀌는 곳이 적지만 예약 1건이 여전히 "레슨의 한 시간"이라, 레슨 단위로 해야 하는 일(확정·취소·완료·차감)을 전부 묶음 기준으로 다시 맞춰야 하고 그중 하나라도 빠지면 같은 문제가 다시 생긴다. 이번 작업은 변경을 줄이는 것이 아니라 예약 기능을 바로잡는 것이 목적이어서, 범위가 크더라도 모델을 실제와 맞추는 B 를 골랐다.

## 6. 수정

**DB** — 마이그레이션 `b3c4d5e6f8a9`

- `booking_slots` 신설: 예약이 차지하는 시간 한 칸씩(예약, 슬롯, 날짜, `holds_slot`). 2시간 레슨이면 예약 1건에 2행이다.
- 유니크 인덱스 `uq_booking_slots_slot_date`: 같은 날짜·슬롯을 차지하는(`holds_slot`) 예약은 하나. `bookings` 에 있던 인덱스를 옮긴 것이다. 예약 상태는 `bookings` 에 있어 인덱스 조건으로 쓸 수 없으므로, 예약이 취소되면 같은 트랜잭션에서 `holds_slot` 을 끈다.
- `bookings.calendar_id` 추가: 예약이 속한 캘린더. 지금까지는 슬롯을 거쳐 찾았는데, 슬롯이 여러 개가 되면서 예약이 직접 갖게 했다. 캘린더가 지워지면 예약도 함께 지워지는 동작(전에는 슬롯을 거친 CASCADE)도 이 칸이 이어받는다.
- `bookings.time_slot_id` 와 그 인덱스 제거. 기존 예약은 각자 슬롯 1개짜리 예약으로 옮겼다.
- 롤백: 가능하지만 여러 시간 예약은 첫 시간만 남는다(나머지 시간 정보 손실). 운영 DB 에서는 쓰지 않는다.

**백엔드**

- `backend/app/domains/booking/models.py`: `BookingSlot` 추가, `Booking.time_slot_id` → `calendar_id`.
- `backend/app/domains/booking/schemas.py`: 요청 `time_slot_ids`(1~12개), 응답 `time_slot_ids`·`start_time`·`end_time`.
- `backend/app/domains/booking/repository.py`
  - `create`: 슬롯 확인(`_lesson_slots`: 같은 캘린더, 켜진 슬롯, 그 요일, 서로 이어짐) → 휴무 확인 → 수강권 고정 → 예약과 슬롯을 한 트랜잭션으로 저장. 하나라도 걸리면 예약이 남지 않는다.
  - `_pin_pass`: 쓸 수 있는 수강권 중 회당 시간이 슬롯 수와 같은 것을 고른다. 쓸 수 있는 수강권이 없으면 409, 있는데 시간이 다르면 400.
  - `_transition`: 취소로 바뀌면 그 예약의 `holds_slot` 을 끈다.
  - `read`·`read_many`: 응답에 슬롯과 시작·끝 시각을 붙인다.
  - 완료·노쇼·차감·남은 횟수 계산은 바꾸지 않았다. 이미 예약 1건 단위였다.
- `backend/app/domains/calendar/repository.py`: 가용 시간, 휴무 처리 전 예약 확인, 슬롯 삭제 확인을 `booking_slots` 기준으로.
- `backend/app/domains/instructor/repository.py`, `lesson_notes/repository.py`: 예약의 강사를 `calendar_id` 로 찾는다.
- `backend/alembic/env.py`: 빈 DB 구축 때 옛 마이그레이션이 참조하는 `bookings.time_slot_id` 를 잠시 붙인다.

## 8. 남은 것

- 슬롯 1개를 1시간으로 본다(슬롯 수 = 수강권의 회당 시간). 기본 슬롯은 1시간 단위지만 강사가 길이가 다른 슬롯을 만들 수 있고, 그 경우 "2시간 수강권 = 슬롯 2개"가 실제 2시간이 아닐 수 있다. 슬롯 길이를 1시간으로 고정할지, 시간 합으로 비교할지는 따로 정한다.
- 화면 동작(확인 창, 2시간 예약 표시)은 이번에 브라우저로 한 번 확인했지만 반복해서 도는 자동 테스트는 없다. 두 앱과 웹은 타입 검사만 한다.
- `backend/scripts/seed_dev_data.sql` 은 예약을 직접 넣는 옛 형식이라 지금 스키마에서 실행되지 않는다(수강권 고정 제약이 생긴 뒤부터). 데모 데이터는 `seed_demo.py` 를 쓴다.
- 강사 앱 일괄 완료, 409 거부 이유 화면 표시는 별도 작업.

## 9. 배운 것

처음에는 "2시간 수강권을 완료하면 2회 차감된다"는 증상만 보고 차감하는 코드를 고치면 된다고 생각했다. 그런데 따라가 보니 원인은 차감이 아니라 "레슨 1회"를 나타내는 데이터가 없다는 것이었고, 반쪽만 예약되는 문제와 강사 앱이 묶음의 첫 예약만 처리하는 문제도 같은 곳에서 나오고 있었다. 그래서 변경을 줄이는 대신 예약 1건을 레슨 1회로 만드는 쪽을 골랐는데, 그러고 나니 차감·남은 횟수·상태 전환 코드는 고치지 않았는데도 맞게 동작했다. 증상이 보이는 곳과 고쳐야 할 곳이 다를 수 있다는 것을 알았다. 예약 구조를 바꾸는 큰 변경이었지만 앞 작업에서 만든 테스트 218개가 기대값을 바꾸지 않고 통과해, 테스트는 만들 때보다 나중에 그 밑을 바꿀 때 더 쓸모 있다는 것도 겪었다.
