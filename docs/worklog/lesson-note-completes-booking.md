# 레슨노트 작성 = 레슨 완료

- 상태: 완료
- 기간: 2026-11-23 ~ 2026-11-24
- 브랜치 / PR: `crm` / #96
- 관련 작업: [일괄 완료](booking-bulk-complete.md), [예약 날짜 규칙](booking-date-rules.md), [예약 시 수강권 고정](booking-pass-pinning.md)

## 1. 문제

강사는 레슨이 끝나면 두 가지를 따로 한다. 대시보드에서 예약을 완료 처리하고, 레슨노트 탭에서 노트를 쓴다.
둘은 같은 레슨에 대한 일인데 화면도 요청도 따로라서, 노트만 쓰고 완료를 잊으면 수강권이 차감되지 않은 확정 예약이 남는다.

서버에는 노트를 예약에 연결하는 칸(`lesson_notes.booking_id`, 예약당 하나)이 이미 있다. 하지만 연결만 할 뿐 예약 상태는 건드리지 않고, 강사 앱·웹 어디에서도 이 칸을 보내지 않는다.
아직 수업 전인 확정 예약에도 노트가 달린다.

## 2. 테스트 명세

"어떤 상황에서 → 무엇이 일어나야 한다" 형식. 요청은 모두 강사가 예약 번호를 넣어 레슨노트를 저장하는 것이다.

- [ ] 1. 수업 당일인 내 확정 예약에 노트를 저장하면 → 201 을 반환하고 노트가 저장되며, 예약은 완료 상태가 되고 고정된 수강권이 1회 차감된다
- [ ] 2. 수업 날짜가 아직 오지 않은 확정 예약에 노트를 저장하면 → 409 로 거부되고 노트는 저장되지 않으며, 예약은 확정 그대로이고 수강권은 차감되지 않는다
- [ ] 3. 고정된 수강권을 다 쓴 확정 예약에 노트를 저장하면 → 409 로 거부되고 노트는 저장되지 않으며, 예약은 확정 그대로이고 사용 횟수도 그대로다
- [ ] 4. 이미 완료된 예약에 노트를 저장하면 → 201 을 반환하고 노트만 저장되며, 수강권은 더 차감되지 않는다
- [ ] 5. 노쇼·취소된 예약에 노트를 저장하면 → 400 으로 거부되고 노트는 저장되지 않는다
- [ ] 6. 같은 확정 예약에 노트 저장 요청 두 개가 동시에 오면 → 하나만 201 이고 다른 하나는 409 다. 노트는 1개만 남고 수강권은 1회만 차감된다
- [ ] 7. 노트 저장과 대시보드의 완료 요청이 같은 예약에 동시에 오면 → 예약은 완료 상태가 되고 수강권은 1회만 차감된다. 노트 저장이 거부(409)됐다면 노트는 남지 않는다

## 4. 원인

`LessonNoteRepository.create` 는 예약이 확정·완료 상태인지와 본인 캘린더의 예약인지만 확인하고 노트를 저장했다. 예약 상태를 바꾸거나 수강권을 차감하는 코드가 없었고, 수업 날짜도 보지 않았다.

## 5. 선택지와 결정

**완료·차감이 거부되면 노트는 어떻게 하는가**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 노트도 저장하지 않는다 (둘 다 되거나 둘 다 안 됨). 쓰던 글은 강사 앱이 기기에 임시저장 | 서버에 "노트는 있는데 완료는 안 된 예약"이 생기지 않는다. DB·API 변경 없음 | 임시저장이 기기에만 있어 기기를 바꾸거나 앱을 지우면 사라지고 웹에서는 안 보인다 |
| B. 노트도 저장하지 않고, 서버에 임시저장 칸을 둔다 | 기기를 바꿔도 남고 웹에서도 보인다 | 마이그레이션 필요. 임시저장이 고객에게 보이지 않게 하는 규칙, 임시저장 → 정식 저장 전환, 취소된 예약에 붙은 임시저장 옮기기 등 규칙이 늘어난다 |
| C. 노트는 저장하고 완료만 실패로 알린다 | 쓴 글이 바로 남는다 | 예약당 노트가 하나라 그 예약은 다시 "노트로 완료"할 수 없다. 응답에 완료 실패를 알리는 칸이 새로 필요하다 |

- 고른 것: A
- 이유: 예약 하나에 노트는 하나라서, 노트만 먼저 남으면(C) 그 예약은 다시 노트로 완료할 수 없고 "노트는 있는데 차감은 안 된 레슨"이 남는다. 이번 작업이 없애려던 상태가 바로 그것이다. 서버 임시저장(B)은 고객에게 보이지 않게 하는 규칙과 정식 저장으로 바꾸는 규칙까지 새로 정해야 해서, 거부가 드문 지금은 기기 저장으로 충분하다고 봤다. 기기를 바꾸면 사라지는 것은 감수한다

**수업 전인 확정 예약에 노트를 연결하려고 하면**

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 거부한다 (완료 날짜 규칙과 같음) | "예약에 연결한 노트 = 완료된 레슨"이 항상 성립한다 | 수업 전 메모는 예약 연결 없이 고객별 노트로 써야 한다 |
| B. 노트만 저장하고 완료는 하지 않는다 | 지금 동작 그대로 | 같은 동작이 날짜에 따라 결과가 다르고, 그 예약은 나중에 "노트로 완료"할 수 없다 |

- 고른 것: A
- 이유: 대시보드의 완료는 수업 당일부터만 된다. 노트로 하는 완료가 이 규칙을 비켜 가면 같은 예약이 경로에 따라 다르게 처리된다. 수업 전에 적어 둘 메모는 예약에 연결하지 않은 고객별 노트로 쓸 수 있다

## 6. 수정

- 바꾼 파일:
  - `backend/app/domains/lesson_notes/repository.py`: `create` 가 확정 예약에 연결된 노트면 예약 완료(상태 전환 + 수강권 1회 차감)를 먼저 하고, 노트와 함께 한 번에 commit 한다. 완료가 409 로 거부되면 노트는 추가되지 않는다. 완료된 예약에 노트 저장이 동시에 와서 유니크 제약에 걸리면 409 로 바꾼다
  - `backend/app/domains/booking/repository.py`: `complete` 를 commit 전 단계(`complete_uncommitted`)와 commit 후 단계(`announce_completed`: 사용 로그·고객 푸시)로 나눴다. `complete` 의 동작은 그대로다
  - `backend/tests/test_lesson_note_complete.py` (신규), `backend/tests/test_lesson_notes.py` (확정 예약에 노트를 쓰는 테스트가 수업 전 날짜였어서, 날짜를 수업 뒤로 옮김)
  - 강사 앱: `app/(tabs)/notes.tsx`(완료할 레슨 선택, 저장 전 확인, 임시저장 불러오기·목록), `app/(tabs)/index.tsx`("완료할 레슨" 줄의 "노트 작성" 버튼, 탭으로 돌아올 때 다시 읽기), `lib/noteDrafts.ts`(기기 임시저장), `lib/lessonText.ts`
- 영향 범위 (API 계약, DB, 웹·앱):
  - API: `POST /lesson-notes` 의 요청·응답 모양은 그대로. `booking_id` 를 넣었을 때의 동작이 바뀐다 (확정 예약 → 완료·차감, 수업 전·수강권 없음 → 409)
  - DB: 변경 없음
  - 웹·고객 앱: 변경 없음. 두 곳 모두 `booking_id` 를 넣어 노트를 만들지 않는다
