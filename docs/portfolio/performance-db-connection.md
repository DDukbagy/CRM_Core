# 성능 개선: 앱 화면이 열릴 때마다 1~2초 멈추던 문제

> 2026-10-05 · 백엔드(FastAPI + SQLAlchemy async + asyncpg) ↔ Supabase Postgres(Session pooler)

## 1. 증상

고객 앱·강사 앱에서 화면을 열거나 탭을 옮길 때마다 짧게(1~2초) 로딩이 걸렸다. 몇몇 화면은 다시 들어올 때마다 화면 전체가 로딩 표시로 바뀌었다.

## 2. 원인 찾기 — 감으로 고치지 않고 먼저 쟀다

"앱이 느리다"는 앱·네트워크·백엔드·DB 어디든 원인일 수 있어서, 아래에서 위로 한 단계씩 시간을 쟀다.

| 측정 | 결과 | 해석 |
|---|---|---|
| DB 없는 API(`/health`) | 3~6ms | 백엔드 자체와 네트워크(로컬)는 빠름 |
| 이미 연결된 상태에서 쿼리 1번 | **77ms** | Codespace(개발 서버)와 Supabase 사이 왕복 시간 |
| **새 DB 연결** + 쿼리 1번 | **약 860ms** (첫 연결 1.7초) | 연결할 때마다 TLS 핸드셰이크 + 인증으로 왕복이 여러 번 |
| 실제 API(`GET /calendars/{강사}/availability`, 쿼리 5개) 10번 | 평균 **1,473ms** | 대부분이 연결 비용 |
| 화면 하나가 부르는 API 4개 동시 | **1.5~2.5초** | 사용자가 느낀 "멈춤" |

코드를 보니 DB 엔진이 `NullPool` 이었다. 연결을 재사용하지 않고 **요청마다 Supabase 에 새로 연결**하는 설정이다.

```python
# 이전 (app/db/session.py)
create_async_engine(db_url, poolclass=NullPool, ...)
```

주석에 남은 이유는 "오래 놀던 연결을 pooler 가 끊어서 다음에 쓸 때 SSL TimeoutError 가 났다"였다. 오류를 피하려고 연결 재사용 자체를 꺼 버린 것이 원인이었다.

## 3. 해결

### 3.1 커넥션 풀로 바꾸고, 예전 오류는 다른 방법으로 막기

```python
# 이후
create_async_engine(
    db_url,
    pool_size=5, max_overflow=5,   # 프로세스당 최대 10개 (Supabase 연결 한도 안에서)
    pool_pre_ping=False,           # 3.2·3.3 참고
    pool_recycle=300,              # 5분 넘은 연결은 버리고 새로 맺음
    pool_timeout=10,
)
```

- 연결을 재사용하므로 요청마다 드는 860ms 연결 비용이 없어진다.
- "놀던 연결이 끊긴" 오류는 연결을 쓰지 않는 방식(NullPool)이 아니라, **끊긴 연결을 미리 걸러 내는 방식**으로 막는다.

### 3.2 `pool_pre_ping` 은 쓸까 말까 — 이것도 쟀다

`pool_pre_ping` 은 연결을 꺼낼 때마다 살아 있는지 확인하는 옵션이다. 안전하지만 확인하는 만큼 왕복이 늘어난다.

| 설정 | 새 세션 + 쿼리 1개 |
|---|---|
| `pool_pre_ping=True` | 478ms |
| `pool_pre_ping=False` | 226ms |

확인 비용이 요청마다 약 250ms 였다. 그래서 "정말 놀던 연결이 끊기는가"를 직접 시험했다.

(시험 결과와 최종 설정은 §3.3)

### 3.3 놀던 연결이 실제로 끊기는가

연결 하나를 맺어 두고 1·3·6·10분 동안 쓰지 않은 뒤 다시 써 봤다 (원격 Supabase, Session pooler).

| 쉰 시간 | 결과 |
|---|---|
| 1분 | 정상 |
| 3분 | 정상 |
| 6분 | 정상 |
| 10분 | 정상 |

10분까지 끊긴 연결이 없었다. 그래서 다음과 같이 정했다.

- `pool_recycle=300`: 5분이 넘은 연결은 꺼내기 전에 버리고 새로 맺는다. 실측으로 확인된 10분보다 충분히 짧다.
- `pool_pre_ping=False`: 요청마다 드는 확인 비용(약 250ms)을 없앤다.

그래도 DB 재시작처럼 연결이 갑자기 끊기는 경우는 남는다. 이것도 로컬 DB에서 풀에 있던 연결을 DB 쪽에서 강제로 끊어(`pg_terminate_backend`) 시험했다.

| 순서 | 결과 |
|---|---|
| 끊긴 뒤 1번째 요청 | 실패 (`InterfaceError`) |
| 2번째 요청 | 정상 (새 연결) |
| 3번째 요청 | 정상 |

끊긴 연결을 쓴 요청 **하나만** 실패하고, SQLAlchemy 가 풀을 비워 다음 요청부터 새로 연결한다. 실패한 요청은 트랜잭션째 롤백되므로 결제·예약 데이터가 반쯤 저장되는 일은 없다. 이 드문 1회 실패와 모든 요청의 250ms 를 비교해 끄는 쪽을 택했다. 운영에서 끊김이 잦아지면 `pool_pre_ping=True` 한 줄로 되돌릴 수 있다.

### 3.4 앱: 다시 들어올 때마다 전체 로딩 표시하던 화면 4곳

대부분 화면은 **처음 한 번만** 로딩 표시를 하고, 다시 들어오면 기존 내용을 보여 둔 채 뒤에서 새로 불러온다. 4곳(고객 수강권·채팅 목록, 강사 수강권 관리·채팅 목록)만 매번 `setLoading(true)` 로 화면 전체를 로딩으로 바꾸고 있어 같은 방식으로 맞췄다.

## 4. 결과

같은 API(`GET /calendars/{강사}/availability`)를 원격 Supabase 로 쟀다. 서버를 켠 뒤 첫 요청은 연결을 처음 맺으므로 세 경우 모두 약 2.3초로 같고, 아래는 두 번째 요청부터의 값이다.

| 단계 | 요청 1개 (순차 평균) | 화면 하나 (API 4개 동시) |
|---|---|---|
| 이전: `NullPool` | 1,473ms | 1.5~2.5초 |
| 커넥션 풀 + `pool_pre_ping=True` | 781ms | 약 0.85초 |
| **최종: 커넥션 풀 + `pool_pre_ping=False`** | **548ms** | **약 0.57초** |

- 요청 하나가 **약 63% 빨라졌고**(1,473 → 548ms), 화면 하나를 여는 시간은 **최대 2.5초에서 0.6초 안쪽**이 됐다.
- 남은 548ms 는 쿼리 5개 × 왕복 77ms 와 트랜잭션 시작·끝 왕복이다. 개발 서버와 DB 사이 거리 때문이라 운영 배치(같은 리전)에서 더 줄어든다.
- 백엔드 테스트 182개와 원클릭 로컬 검증(`make apiverify`) 통과. 앱 두 개 타입 검사 통과.

## 5. 배운 것

- **오류를 없애려고 기능을 끄면 다른 비용이 생긴다.** SSL 타임아웃을 피하려고 연결 재사용을 끈 결과, 모든 요청이 느려졌다. 오류의 원인(끊긴 연결을 다시 씀)만 정확히 막는 옵션(`pool_pre_ping`/`pool_recycle`)이 있었다.
- **측정 → 원인 → 수정 → 다시 측정.** 각 단계(API 자체 / 쿼리 왕복 / 연결 비용 / 안전장치 비용)를 따로 재니 어디에 시간이 쓰이는지가 숫자로 보였고, 안전장치(`pool_pre_ping`)를 쓸지 말지도 실험으로 정할 수 있었다.
- **개발 환경의 거리는 운영에서 줄어든다.** 쿼리 왕복 77ms 는 개발 서버(Codespace)와 DB 가 다른 지역이라서다. 운영에서 백엔드를 DB 와 같은 리전에 두면 왕복은 수 ms 로 줄고, 이번 개선(연결 재사용)은 그대로 유효하다.
