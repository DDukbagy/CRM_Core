# 개선 계획 (2026-11 포트폴리오 피드백 반영)

> 작성 2026-11-13. 포트폴리오 피드백을 받고 정한 작업 방향과 순서다.
> 이 문서는 **무엇을 어떤 순서로 할지**를 다룬다. 작업마다 남기는 기록은 `docs/worklog/` 양식을 따른다.

## 1. 왜 하는가

받은 피드백의 요지는 세 가지다.

1. **성능 수치의 신뢰도** — "API 평균 1,473ms → 548ms"는 10회 평균이라 지연 분포를 보여 주지 못한다. 부하 테스트로 p50·p95·p99 를 개선 전후로 제시해야 한다.
2. **동시 요청** — 예약 완료와 수강권 차감을 한 트랜잭션으로 묶은 것(원자성)은 좋지만, 동시에 들어오는 요청은 막지 못한다.
3. **AI 검증 체계** — "pytest N개 통과"는 강점이 아니다. AI 가 만든 테스트는 통과하지만 아무것도 검증하지 않을 수 있다. 사람이 테스트 명세를 쓰고, 실제 DB 에서 검증하는 체계를 보여 줘야 한다.

## 2. 작업 원칙 (Claude Code 가 지킬 것)

`CLAUDE.md` 의 규칙(영향 범위 보고 → 승인, 한 항목 = 한 브랜치, env 파일 열람 금지)은 그대로 적용한다. 여기에 아래를 더한다.

1. **테스트 명세는 사용자가 쓴다.** 핵심 규칙(수강권 차감, 예약 상태 전환, 휴무)의 "무엇을 검증할지"는 사용자가 worklog 의 `테스트 명세` 칸에 직접 적는다. Claude Code 는 그 명세를 테스트 코드로 옮기고 구현만 한다. 명세에 없는 케이스가 필요해 보이면 추가하지 말고 **제안**한다.
2. **실패하는 테스트가 먼저다.** 문제를 고치기 전에 그 문제를 재현하는 테스트를 만들어 실패를 확인하고, 그 출력을 worklog 에 붙인다. 그다음 수정한다.
3. **커밋을 나눈다.** `test: 실패 재현` → `fix: 수정` 순서로 나눠, 이력만 봐도 재현 후 수정했음이 드러나게 한다.
4. **모킹으로만 통과하는 테스트를 만들지 않는다.** 핵심 규칙 테스트는 로컬 Postgres 컨테이너에서 실제 쿼리로 검증한다.
5. **수치는 측정한 것만 적는다.** 측정하지 않은 수치, 예상 수치를 worklog 나 포트폴리오 문구에 쓰지 않는다. 측정 조건(환경, 데이터 건수, 동시 사용자 수, 실행 시간)을 함께 적는다.
6. **원격에 부하를 걸지 않는다.** 부하 테스트와 더미 데이터 적재는 로컬 Postgres 에서만 한다. 데모(Render·Supabase)와 개발용 Supabase 에는 대량 요청·대량 적재를 하지 않는다.

## 3. 순서

앞 단계의 결과가 뒤 단계의 재료가 되도록 잡았다. 한 단계가 끝나면 worklog 를 완성하고 다음으로 넘어간다.

| 순서 | 작업 | 구분 |
|---|---|---|
| 1 | 동시 요청 문제: 테스트 명세 → 실패 재현 → 수정 | 필수 |
| 2 | 보안 수정: HS256 폴백 평소 끄기, 웹 쿠키 HttpOnly 검토 | 권장 |
| 3 | 로깅 체계: JSON 구조화 로그 + 요청 ID | 권장 |
| 4 | 더미 데이터 + 부하 테스트(p50·p95·p99) | 권장 |
| 5 | 토스페이먼츠 연동 | 선택 |

### 3.1 동시 요청 문제 (필수)

**현재 코드 (staging `465bbd7` 기준)**

- `backend/app/domains/passes/repository.py` 의 `deduct_for_lesson` 은 "수강권을 읽고 → `sessions_used += 1` → 저장" 방식이다.
- `backend/app/domains/booking/repository.py` 의 상태 전환(`complete`, `mark_no_show`, `confirm` 등)은 "읽고 → 상태 확인 → 저장" 방식이다.
- 행 잠금(`with_for_update`), 조건부 UPDATE, 동시 호출 테스트가 없다. 격리 수준은 PostgreSQL 기본값(READ COMMITTED)이다.

**예상되는 증상**

- 같은 수강권을 쓰는 예약 두 건이 동시에 완료되면 차감 1회가 사라진다 (갱신 손실).
- 같은 예약에 완료 요청이 두 번 동시에 오면 둘 다 `CONFIRMED` 를 읽고 통과해 이중 차감된다.
- 저장 전에 `sessions_used < sessions_total` 을 확인하므로 "잔여 -1" 형태로는 나타나지 않을 가능성이 높다. 실제 증상은 테스트로 확인한다.

**진행**

1. 사용자가 worklog 에 테스트 명세를 적는다. (예: "잔여 1회 수강권에 완료 2건이 동시에 오면 1건만 차감된다", "같은 예약 완료를 동시에 2번 보내면 1번만 성공한다")
2. 동시 요청 테스트를 만든다. **요청마다 독립된 DB 세션(연결)** 을 써야 한다. 한 세션을 공유하면 동시 실행이 되지 않아 문제가 재현되지 않는다. `asyncio.gather` 로 동시에 호출한다.
3. 실패를 확인하고 출력을 worklog 에 붙인 뒤 커밋한다.
4. 수정안의 영향 범위를 보고하고 승인받는다. 후보:
   - 상태 전환: `UPDATE ... WHERE id = :id AND status = 'CONFIRMED'`, 영향받은 행이 0이면 409
   - 차감: `SET sessions_used = sessions_used + 1 WHERE ... AND sessions_used < sessions_total`
   - 대안: `SELECT ... FOR UPDATE` (비관적 락). 둘 중 무엇을 왜 골랐는지 worklog 에 적는다.
5. 응답 코드가 바뀌면 API 계약 변경이다. 웹과 두 앱의 오류 처리에 영향이 있는지 확인한다.
6. 같은 테스트가 통과하는 것을 확인하고 출력을 worklog 에 붙인다.

**같이 공부할 것 (사용자)**: 트랜잭션 격리 수준, 갱신 손실, 비관적 락과 낙관적 락, PostgreSQL(READ COMMITTED)과 MySQL(REPEATABLE READ)의 기본값 차이.

### 3.2 보안 수정 (권장)

- **HS256 폴백**: `backend/app/core/auth/deps.py` 는 Supabase 검증이 실패하면 로컬 HS256 토큰 검증(`_verify_local_hs256_token`)을 시도한다. `CLAUDE.md` 10.3 은 이것을 긴급 대응 수단으로 규정한다. 평소에는 꺼 두고 명시적으로 켰을 때만 동작하도록 바꾼다. 인증 로직 변경이므로 영향 분석을 먼저 한다. 테스트가 이 폴백에 의존하는지부터 확인한다.
- **웹 쿠키 HttpOnly**: 웹은 Supabase 세션 쿠키를 쓰고, `/api/[...path]` 프록시가 쿠키에서 토큰을 꺼내 `Authorization` 헤더로 바꿔 백엔드에 보낸다. 먼저 현재 쿠키 속성과, 브라우저 쪽 코드가 세션 쿠키를 직접 읽는 곳이 있는지 조사해 보고한다. 조사 결과에 따라 범위를 정한다. 모바일 앱은 쿠키를 쓰지 않으므로 대상이 아니다.

### 3.3 로깅 체계 (권장)

- 로그를 JSON 한 줄 형식으로 남긴다.
- 미들웨어에서 요청마다 요청 ID 를 만들고(또는 받은 헤더 값을 쓰고), 응답 헤더에도 넣는다. 응답이 나갈 때 메서드·경로·상태 코드·처리 시간(ms)을 기록한다.
- 로그를 두 종류로 나눈다: 장애 로그(오류, 지연)와 사용 로그(예약 생성, 완료, 차감 같은 행동).
- **토큰, 비밀번호, 이메일·전화번호 같은 개인정보는 로그에 남기지 않는다** (`CLAUDE.md` 3, 4절). 사용자 식별은 ID 로만 한다.
- 부하 테스트에서 느린 요청을 추적하는 데 쓰므로 3.4 보다 먼저 한다.

### 3.4 더미 데이터 + 부하 테스트 (권장)

- 더미 데이터 스크립트: 로컬 Postgres 에 회원·강사·수강권·예약을 넣는다. 소진된 수강권, 휴무일, 노쇼 예약처럼 현실적인 분포를 섞는다. 다시 실행해도 같은 상태가 되도록 만든다.
- 부하 도구: Locust (Python). 시나리오 예: 로그인 → 가용 시간 조회 → 예약 생성. 조회가 쓰기보다 자주 일어나도록 비중을 둔다.
- 비교 대상: `NullPool`(개선 전)과 커넥션 풀 5+5(개선 후). **같은 데이터, 같은 가상 사용자 수, 같은 실행 시간**으로 측정한다.
- 결과: 엔드포인트별 p50·p95·p99 와 실패율. 가상 사용자를 단계적으로 늘려 풀 크기가 버티는 지점을 본다.
- 로컬 측정값은 실서비스 수치가 아니다. 측정 조건을 항상 함께 적는다.
- 기존 기록 `docs/portfolio/performance-db-connection.md` 는 지우지 않고, 새 측정 결과를 이어서 적는다.

### 3.5 토스페이먼츠 연동 (선택)

- `docs/operations/pg-integration.md` 를 먼저 읽는다.
- 결제는 멱등성과 웹훅 중복 처리가 핵심이다. 3.1 에서 쓴 조건부 UPDATE 방식이 그대로 이어진다.
- 1~4 단계가 끝난 뒤에 시작한다.
